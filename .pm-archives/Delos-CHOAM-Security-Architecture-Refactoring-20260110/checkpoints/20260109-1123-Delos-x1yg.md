**Key Constraint Documentation**:

#### Push Constraints (5 items)
- Never call from @Entry or @Exit (causes eliding)
- Cannot push null state
- Cannot exceed max depth (16)
- Cannot push if another push pending
- Cannot push if pop pending

#### Pop Constraints (5 items)
- Never call from @Entry or @Exit (causes eliding)
- Cannot pop if stack empty
- Cannot pop if another pop pending
- Cannot pop if push pending
- Cannot pop from wrong state context

#### Symmetry Principle Documented
```
PUSH:  StateA suspended (no exit) → Stack: [StateA]
       StateB enters (entry action runs)

POP:   StateB exits (exit action runs)
       StateA restored (no entry action)
```

#### Transition Eliding Behavior Documented
- When push/pop called from @Entry/@Exit, state becomes "pinned"
- Pending transitions are skipped/elided
- This is a safety mechanism to prevent conflicting nesting
- Code location: `Fsm.java:531-535`

### 6. Documented Design Rationale

**Why separate push/pop from normal transitions?**
- Subroutine call model (save/restore state exactly)
- StateA calls StateB as subroutine, resumes after

**Why no exit on push?**
- State is suspended, not exited
- Would need re-enterable semantics (complex)
- Single @Exit sufficient for protocols

**Why no entry on pop?**
- State was never exited, just suspended
- Re-running entry would be incorrect initialization

**Why pending transitions?**
- Separates state initialization from state change request
- Allows entry action to modify state without triggering transitions

## Key Insights Documented

### 1. State Stack Saves BOTH State and Context
- Each stack entry is `State<Context, Transitions>` object
- Saves the enum value AND the full context
- Allows restoration to exact previous state
- Critical for protocol correctness

### 2. Push and Pop Are NOT Regular Transitions
- Normal: Exit(A) → State=B → Entry(B)
- Push: [no Exit(A)] → Save A → State=B → Entry(B)
- Pop: Exit(B) → State=A → [no Entry(A)]
- Fundamentally different semantics

### 3. Pending Transitions Enable Clean Separation
- Entry/Exit action = state initialization/cleanup
- Transition firing = state change request
- Proxy captures ONE method call
- Transition fires after Entry/Exit completes

### 4. Transition Eliding Is a Safety Mechanism
- If push/pop called from @Entry/@Exit, state becomes "pinned"
- Pending transitions are skipped/cancelled
- Prevents conflicting nested transitions
- Code explicitly logs when eliding occurs

### 5. Maximum Stack Depth Prevents DoS
- Limit of 16 levels prevents:
  - Unbounded memory growth
  - Stack overflow attacks
  - Accidental infinite push loops
- Enforced with `IllegalStateException`

### 6. Symmetry Principle for Correctness
- Push suspends State A (no exit)
- Pop restores State A (no entry)
- Symmetric operations guarantee exact restoration
- Critical for Byzantine protocol correctness

## Learnings

### 1. Tron FSM Is Sophisticated Design
- Push/pop enable subroutine-like state nesting
- Complete context preservation allows exact state restoration
- Pending transitions provide clean execution model
- Transition eliding prevents ambiguous nesting

### 2. State Stack Semantics Critical for Byzantine Safety
- All replicas must execute push/pop identically
- Symmetric Entry/Exit behavior ensures consistency
- Bounded stack depth prevents resource exhaustion
- Pending transition model supports deterministic execution

### 3. Constraints Prevent Subtle Bugs
- Forbidding push/pop from Entry/Exit prevents eliding
- Single @Entry/@Exit per state ensures determinism
- Maximum stack depth prevents DoS attacks
- These constraints work together for safety

### 4. Documentation Pattern Effective
- Real-world examples (Telephone protocol) clarify semantics
- Execution order diagrams make behavior clear
- Constraint checklists prevent violations
- Cross-references help developers find related information

### 5. Byzantine Considerations Drive Design
- Determinism required for replica consistency
- Complete state preservation needed for recovery
- Bounded resources prevent attack vectors
- Synchronous pending transitions ensure protocol progress
